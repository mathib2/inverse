# Sponsor technology: where each one does real work

The submission asks how Zetaris, Meterless, Cursor and NVIDIA are used. Every row names the code and the evidence; nothing listed here is a mention without a code path and a test.

## Zetaris (data)

**What it does:** it is the only data path. The equipment registry, the sensor specifications, the sensor samples and the maintenance history are REST tables that Zetaris federates from the team's `obs-service`, cached with `CACHE TABLE` and exposed through schemastore views. Scout and Ada query them read-only through a guard (one SELECT on known tables only; every table behind an alias or a comma checked; subqueries refused); maintenance notes pass the injection guard before any model sees them; Warden's "new data" check is a Zetaris query per machine.

**Where:** `core/inverse_core/clients/zetaris.py`, `data/zetaris/*.sql` (REST tables, cache, views), `scripts/admin/setup_zetaris.py` (idempotent setup), `core/inverse_core/team/sql_guard.py: check_sql` and `team/tools.py: Tools._run_sql` (the `run_sql` tool), `core/inverse_core/team/watch.py: Watcher.fingerprint`.

**Evidence:** `tests/test_guard.py` (the SQL guard: known tables only, every table behind an alias or a comma, subqueries and Spark built-ins refused), `tests/test_integration.py` (a live registry query), every query in a mission's files (Scout's as `sql` evidence in `plan.json`, the `run_sql` tool's as `tool` events in the trace), `smoke_test.py`.

**Honest note:** the federated source is one synthetic service; the data is seeded and documented in `data/README.md`.

## NVIDIA Nemotron (reasoning)

**What it does:** every model call of the live crew runs on Nemotron-Mini-4B-Instruct: through Nightshift on a laptop GPU, or, when Nightshift cannot answer, served by Ollama on the workstation. The exception is Tinker, which runs in its own sandbox on Ollama; its engineer step uses `qwen2.5-coder:7b` (`TINKER_ENGINEER_MODEL`). With a hosted Nightshift the `fast`, `deep` and `critic` lanes can map to larger Nemotron routes (`team/lanes.py`). On the Ollama provider a lane can be pointed at another local model (`LANE_CRITIC=qwen2.5:3b-instruct` keeps Vera on a different model). The live crew runs all three lanes on the one Nightshift route, and the fallback always answers with `MODEL_FALLBACK_MODEL`, so there Vera reviews on the same Nemotron as the work; her independence comes from her fixed rules and the code checks that run before her model. The trace always names the served model. The deterministic layer decides (the SQL guard, the number check, Vera's rules, the plan rule, the file-and-line check); Nemotron proposes, explains and reviews.

**Where:** `core/inverse_core/team/lanes.py`, `clients/meterless.py`, `docs/operations/NIGHTSHIFT_TUNNEL.md` (the Nightshift lane, about 59 tokens a second), `docs/operations/LOCAL_MODELS.md` (measured speeds).

**Evidence:** every trace records the served model per call (`llm` events, `models_used`). The benchmark runs the same Nemotron-Mini-4B both ways: 8/8 in 222 s on the workstation's CPU (round 17), 8/8 in 40 s through Nightshift on the laptop's GPU (round 19), and 8/8 in 32 s in rounds 23 and 24 (`docs/BENCH.md`). Nightshift's router may serve a different Nemotron model than the lane asked for; the trace tells the truth.
